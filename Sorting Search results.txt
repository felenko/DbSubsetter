  Local vs Remote source dependency                                                                                                                                                                                                                                                                                                           
  Face search (probe image provided)                                                                                                                                   

  The two source types are searched differently and in parallel (FacialRecognitionEx.cs:1859–1905):

  Column 1: Image used
  Local (L1): Cropped face (croppedImage)
  Remote (SIN/UMBRA): Original full image (originalImage)
  ────────────────────────────────────────
  Column 1: How
  Local (L1): fr.gallery.Identify(croppedImage, ...) — synchronous
  Remote (SIN/UMBRA): FrSearchHelper.BeginSearch(originalImage, sinConnections, ...) — async, runs in parallel
  ────────────────────────────────────────
  Column 1: Result type
  Local (L1): ResultList idListManagedResult — stored in ResultListManaged
  Remote (SIN/UMBRA): Dictionary<source, List<ScoreMap>> — stored in ResultListMap
  ────────────────────────────────────────
  Column 1: When results land
  Local (L1): Immediately after gallery identify
  Remote (SIN/UMBRA): Polled: while (frSearchHelper.IsRunning) Thread.Sleep(200)

  So remote search starts first (non-blocking), then local runs synchronously, then the code waits for the remote to finish before merging. The two image variants are 
  intentional — cropped is more accurate for the local FR engine, original image is sent to remote APIs.

  ---
  Merge — MergeResultListMap() (FaceSearchData.cs:780)

  After both sources finish, results are interleaved round-robin with sequential sortScore:

  Round 1: 1 local (sortScore=0), 1 SIN (sortScore=1), 1 UMBRA (sortScore=2)
  Round 2: 2nd local (sortScore=3), 2nd SIN (sortScore=4), 2nd UMBRA (sortScore=5)
  ...

  Remote sources are processed in alphabetical order (line 811 sortedKeys.Sort()), so if you have SIN and UMBRA, SIN always goes before UMBRA in each round.

  ---
  Final sort for the page display

  When FetchPersonList fetches the 9 items for the current page, at the end (FaceSearchData.cs:694):

  personList.Sort(new PersonScoreComparer(!hasFaceData));

  For face search hasFaceData = true → PersonScoreComparer(false) → useSortScore = false → sorts purely by Score descending (ignoring the interleaved sortScore).      

  So the interleaving only decides which page a result lands on — but within the 9 slots on that page, they are re-ordered highest-score-first regardless of source.   

  ---
  Text / demographic search (no probe image)

  - Local: fr.FetchDemographicLimitedIdList() — local DB query
  - Remote: all sinConnections queried in parallel via finder.searchAsync(), then waited in sequence
  - Results merged by same MergeResultListMap() round-robin interleave
  - But final sort uses PersonScoreComparer(true) → useSortScore = true → preserves the interleaved sortScore order (0,1,2,3...). No score re-sort.

  So for text search the grid shows: local result, then SIN result, then UMBRA result, then next local, etc.

  ---
  FR initialization dependency (local-only guard)

  There's one more dependency in FetchPersonList (FaceSearchData.cs:193):

  shouldFilterLocalResults = hasFaceScores  (true for face search, false for text)

  During face search, local results are skipped if FacialRecognitionEx.frDatabaseUptodate == false (FR DB still building). This is checked via reflection. If filtering
   would empty the page entirely (e.g. only 2 local results available and FR not ready), there's a fallback that shows the local results anyway (line 283) to avoid an 
  empty grid with a non-zero count.

   - Local results come directly from fr.gallery.Identify(...) — the FR engine returns results pre-sorted by similarity score, highest first. So the local              
  resultListManaged before AdjustSortScores is [score=95, score=88, score=76, score=71, ...]                                                                           
  - Remote results come from FrSearchHelper — the remote FR API also returns its candidates sorted by score descending

  AdjustSortScore doesn't reorder anything within a source — it only stretches the spacing between the blocks to create interleaved slots, while keeping the relative  
  order inside each source intact:

  Before adjust (local, n=2):  sortScores = 0, 1, 2, 3, 4, 5 ...
  After AdjustSortScores:                      0, 1, 2, 6, 7, 8 ...  ← gap created for remote

  Remote (offset = 3*1 = 3):  sortScores = 0, 1, 2, 3, 4, 5 ...
  After AdjustSortScore:                       3, 4, 5, 9,10,11 ...  ← slotted into the gaps

  So the final merged order was:

  sortScore 0 → local  #1  (best local match)
  sortScore 1 → local  #2
  sortScore 2 → local  #3
  sortScore 3 → remote #1  (best remote match)
  sortScore 4 → remote #2
  sortScore 5 → remote #3
  sortScore 6 → local  #4
  ...

  However — for face search, PersonScoreComparer(false) runs at the end and re-sorts the 9 fetched results purely by score, which breaks the row grouping within that  
  page. The interleaving really only guaranteed which 9 items landed on which page, not the visual row order on the page itself.

  For text/demographic search it did hold: PersonScoreComparer(true) respects SortScore, so the 3-per-source row grouping was fully preserved on screen.
